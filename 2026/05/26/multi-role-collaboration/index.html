多角色协同：五大模式与跨平台实战

这是「Claude & GPT 多角色协同」系列的第三篇，也是核心篇。本小姐会讲清楚为什么需要多角色、五大经典模式、Claude Code 子代理实战，以及 OpenAI 的多角色编排方案。

为什么需要多角色？

单个 AI 的局限：

  • 上下文污染：什么都让一个 AI 做，它会”分心”
  • 角色混乱：既当架构师又当测试员，必然两头都不专精
  • 难以验证：自己写的代码自己审，bug 当然查不出来
  • token 爆炸：复杂任务塞进一个上下文，性能急速下降

多角色的优势：

  • 关注点分离：每个角色专心做一件事
  • 独立上下文：子代理有自己的窗口，主代理不被污染
  • 可并行：多个角色同时干活，速度翻倍
  • 可审计：每个角色的输入输出都能追溯

五大经典协同模式

模式 ①：Orchestrator-Worker（管弦乐队模式）⭐ 最常用

使用场景：复杂功能开发（从需求→设计→实现→评审）

模式 ②：Pipeline（流水线模式）

特点：前一个角色的输出直接作为下一个角色的输入
适合：流程固定、阶段清晰的任务

模式 ③：Debate / Critic（辩论评审模式）

适合：架构决策、风险评估、产品取舍

模式 ④：Parallel Fan-out（并行扇出）

适合：信息收集、多视角分析

模式 ⑤：Reflection Loop（反思循环）

适合：写作润色、代码优化

Claude Code 子代理（Subagents）实战

什么是 Subagent？

Subagent 是一个独立的 AI 实例，有：

  • 自己的系统提示词（专属角色）
  • 自己的上下文窗口（不污染主对话）
  • 自己的工具权限（按需限制）

主代理用 Agent 工具调度它们，等结果返回。

避坑指南

  1. 不要嵌套太深：Agent 套 Agent 套 Agent，上下文会乱
  2. 明确产出格式：在 prompt 里写清”返回什么”
  3. 传足够上下文：Agent 看不到你的主对话，要主动告诉它
  4. 不让 Agent 做决策：决策权留给主代理（也就是你）
  5. 限制工具权限：Reviewer 不需要 Write，Planner 不需要 Bash

OpenAI 多角色编排实战

姿势 ①：Custom GPTs（零代码）

适合不会编程的笨蛋。在 ChatGPT Plus 里：

  1. 点 “Create a GPT”
  2. 给每个角色建一个 GPT
  3. 在对话里 @提及 不同 GPT 协作

姿势 ②：Assistants API（编程接入）

姿势 ③：Swarm（OpenAI 官方实验性框架）

框架对比

框架 优势 劣势 适合
Custom GPTs 零代码 手动切换 非技术用户
Assistants API 官方支持 编排需自己写 中级开发者
Swarm 轻量直观 实验性，功能少 学习入门
AutoGen 微软出品，对话式编排 学习曲线陡 研究型场景
CrewAI 角色清晰，文档好 灵活性一般 生产可用
LangGraph 图结构最灵活 最复杂 复杂工作流

本小姐的建议：先 Swarm 入门 → 再 CrewAI 上手 → 最后 LangGraph 进阶！(*￣︶￣)
